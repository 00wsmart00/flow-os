# AI 制造操作系统产品方向

## 文档状态与目的

本文记录 FlowOS AI 的长期产品方向，为后续开发提供设计依据。本文不改变 V0.1 的范围，不授权使用生产数据，也不替代现有的架构、业务规则和合规基线。

FlowOS AI 应从 AI 辅助的 ERP 工作空间逐步发展为面向中小型服装制造企业的 **AI 制造操作系统（AI Manufacturing Operating System）**：由智能体协调可靠的业务能力，同时由 ERP、MES、WMS 和 PLM 服务继续承担权威数据记录与业务执行职责。

初始架构选择**路线 B：一个核心智能体（Core Agent）加一组独立的专业业务工具**。这种方式使早期交付易于理解和治理，同时保留未来演进为多智能体系统的路径。

## 产品原则

1. **智能体负责理解和协调，业务引擎负责确定性结果。** Core Agent 理解请求、规划任务、选择工具、管理上下文并解释结果。数量、成本、排程、约束和资格判断应来自版本化的业务引擎，而不是模型的自由推理。
2. **业务能力相互独立。** 每个专业工具都应提供有文档的 API，并且可以脱离 Agent 运行。UI、定时任务、系统集成或未来的专业 Agent 都能调用同一能力。
3. **关键业务操作由人掌握最终权力。** 分析和草稿可以自动生成；具有约束力的业务写入必须经过明确授权，并在适用时通过审批。
4. **解释性和可追溯性内建于设计。** 每个结果都必须能说明输入、数据快照、规则或模型版本、工具调用、假设、审批和最终结果。
5. **自然语言与结构化交互结合。** 对话是表达意图的入口，不是完整的产品界面。表格、表单、时间轴、图表、方案对比和审批控件用于呈现并完成业务工作。
6. **逐步提升自主程度。** FlowOS 应通过可衡量的可靠性、受控范围和运行证据逐步获得更高权限。

## 目标架构

```text
自然语言 / 文件 / 业务事件
                    |
                    v
               Core Agent
      理解意图 -> 规划 -> 协调 -> 验证
                    |
        +-----------+-----------+
        |           |           |
        v           v           v
   BOM 与报价     APS 工具     物料与库存
      工具                       工具
        |           |           |
        v           v           v
  确定性成本引擎   排程引擎      MRP / 库存引擎
        +-----------+-----------+
                    |
                    v
              业务服务 API
                    |
                    v
          ERP / MES / WMS / PLM

结构化任务状态和审计事件贯穿所有层级。
```

### Core Agent 的职责

Core Agent 应当：

- 理解用户目标，只获取完成目标所需的上下文；
- 将目标拆分为可以审核的步骤；
- 通过类型明确的契约选择并调用白名单工具；
- 维护任务上下文和可恢复的执行状态；
- 验证工具响应、识别缺失输入并明确表达不确定性；
- 比较不同方案并解释取舍；
- 在规定的控制节点请求确认或审批；
- 为 UI 组装结构化结果。

Core Agent 不应在自由文本中直接计算权威成本、物料缺口或排程结果；不得直接查询数据库、绕过 Service 层授权，也不能仅凭用户在对话中的描述就执行具有约束力的操作。

### 专业工具与确定性业务引擎

每个工具都应是面向一项可独立测试业务能力的轻量、权限感知接口。契约应明确单位、币种、时区、约束集合、规则版本和结果数量上限。API 响应应同时包含结果及解释该结果所需的证据。

示意性的能力边界如下：

```text
build_bom_draft(product_input, assumptions)
calculate_quote(bom_version, quantity, cost_policy, margin_target)
simulate_schedule(order_set, capacity_snapshot, constraint_set)
calculate_material_requirements(order_set, bom_versions, policy_version)
calculate_inventory_gap(requirements, supply_snapshot, allocation_policy)
create_purchase_suggestion_draft(gap_result, purchasing_policy)
```

这些名称仅用于表达概念，并非已经确定的 API 契约。实际端点应遵循仓库现有的版本化 Pydantic 契约、Service、Repository 和纯领域层边界。

## 首批专业工具领域

### BOM 与报价

该工具应将经过授权的产品资料转换为可审核的 BOM 和报价草稿。可使用的输入包括产品文档、图片、技术规格、历史合成数据或授权数据、价格来源、标准工时（SMV）、人工费率、制造费用政策、数量阶梯、损耗和目标毛利率。

权威数值计算必须保持确定性。图片或文档解析只能生成带有来源和置信度的候选字段，不能被系统静默接受为事实。用户必须能够看到缺失输入、计算假设、相似款式、成本构成、价格有效期，以及修改数量或毛利率后的影响。

主要价值指标包括报价周期、单次报价人工操作时间、首次完整率、修改频率，以及报价成本与实际成本之间的偏差。

### APS 排程

该工具应结合订单、工艺路线、产能日历、产线或技能匹配、物料齐套、换线成本、在制品和交期约束进行生产计划模拟。当约束无法满足时，应返回不可行原因，而不是生成虚假的排程结果。

早期版本应以决策支持和方案对比为主。发布或修改生产计划属于受控写入，必须经过授权和审批。

主要价值指标包括排程耗时、准时交付率、计划达成率、产能利用率、换线损失、在制品数量和人工重排次数。

### 物料与库存管理

该工具应结合版本化 BOM 需求，以及合格现存量、占用、保护库存、在途供应、提前期、批次、颜色、单位和采购规则进行分析。系统必须解释每一项短缺，并明确区分物料需求、库存缺口、采购建议和采购订单。

当前 V0.1 的“订单查询 → 库存缺口 → 采购建议草稿”是该领域的第一个窄范围基础。除非经过授权的工作流明确推进，否则建议始终不具有业务约束力。

主要价值指标包括缺料事件、呆滞和过量库存、库存周转率、紧急采购、物料齐套率、计划人员操作时间，以及建议转化为订单的质量。

## 工具独立性与集成规则

- 工具必须通过稳定且有文档的 API 调用，并且不依赖 LLM 或聊天会话。
- 无论调用方是谁，都必须遵守相同的验证、授权、幂等和审计控制。
- 业务规则和数据访问由业务 Service 管理，而不是由提示词管理。
- 在适用场景中，领域计算保持为纯函数，并使用表格驱动测试。
- 长时间计算应使用异步、可恢复任务，不能持续占用对话请求。
- 工具输出使用结构化错误类别，例如缺少输入、未授权、状态无效、不可行、快照过期和依赖临时失败。
- 具有副作用的 API 必须支持幂等，并拒绝过期或已经执行过的审批。
- Agent 只能接收由 Service 组装的白名单最小化数据，不能获取凭证或不受限制的数据存储访问权。

## 权限、审批与任务追溯

### 操作等级

| 等级 | 含义 | 示例 | 默认行为 |
|---|---|---|---|
| L1：读取 | 获取限定范围内的业务信息 | 查看订单、BOM、库存位置或计划状态 | 用户具备权限时执行；按要求记录访问 |
| L2：分析或模拟 | 生成无约束力的结果 | 报价草稿、缺料分析、排程模拟、方案对比 | 明确列出假设后执行，并将结果标记为草稿或模拟 |
| L3：业务写入 | 改变运行状态或创建有约束力的下游对象 | 发布生产计划、批准报价、创建或下达采购订单 | 执行前必须明确确认，并完成基于策略的审批 |

授权必须由实际执行业务操作的 Service 强制实施，不能只依赖 Agent。审批策略还可以考虑角色、租户、金额、风险、职责分离和当前生命周期状态。

### 任务生命周期

持久化任务应在明确的状态之间流转，例如：

```text
草稿 draft -> 就绪 ready -> 运行中 running -> 等待输入 needs_input
           -> 等待审批 awaiting_approval -> 已批准 approved
           -> 执行中 executing -> 已完成 completed
           -> 已拒绝 rejected / 已取消 cancelled / 失败 failed
```

并非每个任务都会经过所有状态。状态流转必须经过验证并产生审计事件。每个任务应保留：

- 发起人和实际操作身份；
- 明确的目标和限定范围内的业务对象；
- 输入引用及快照或版本标识；
- 计划步骤和工具调用；
- 假设、警告以及适用时的置信度；
- 确定性规则或优化算法版本；
- 建议变更及变更前后值；
- 审批请求、审批人、决定和时间；
- 执行结果、失败原因、重试历史及所创建对象的链接。

审计记录必须具备篡改可检测能力，并遵循经过批准的保留策略。敏感值应尽量减少记录，或通过引用关联，而不是复制到日志中。

## 交互模式：自然语言与动态结构化 UI

自然语言应让用户能够方便地表达目标、补充背景并追问。随后，系统应根据任务呈现最合适的业务对象，例如：

- 包含可编辑假设和成本明细的报价工作表；
- 标明物料和产能原因的订单风险表；
- 支持方案比较的交互式排程或甘特图；
- 关联需求与供应证据的缺料表；
- 变更前后并排展示的方案；
- 明确说明具体操作及其后果的审批卡片。

结构化控件应根据服务端定义的 Schema 和策略生成，而不是由模型任意生成可执行 UI。在执行 L3 操作前，UI 必须显示目标对象、关键变更、警告、审批路径和最终明确确认。执行后，对话界面和结构化界面必须体现同一个持久化任务状态。

## 向多智能体演进

在专业化实践能够证明拆分 Agent 可以改善质量或运行效果之前，路线 B 应保持为默认方案。只有当某个领域在规划、上下文、权限、评估或归属责任方面存在显著不同的需求时，才应拆分 Core Agent。

未来可以在监督 Agent 或工作流协调器之下引入 BOM、APS 和库存专业 Agent。它们应复用相同的独立业务工具和 Service API。Agent 之间的消息必须具有明确类型、范围限制和可追溯性，并遵守相同的授权规则；专业 Agent 不能仅因为接受了另一个 Agent 的委派就自动获得更高权限。

多智能体本身不应被视为产品目标。演进过程中必须保留用户可见的任务状态、审批边界、确定性业务引擎和审计证据。

## 分阶段实施

### 阶段 0：可信基础

使用合成数据交付当前窄范围的 V0.1 流程，包括确定性领域规则、类型明确的 API、任务标识、解释性数据和无约束力的草稿。在获准用于生产前，建立身份认证、租户隔离、权限控制、审计事件、可观测性和数据治理能力。

退出证据：计算测试覆盖业务边界；每个结果都能根据保留的版本和快照重新构建；不存在绕过控制的写入路径。

### 阶段 1：Core Agent 查询与分析助手

在白名单 L1 和 L2 工具之上增加 Core Agent。首先支持订单查询、库存缺口解释和采购建议草稿，并增加结构化任务状态、来源记录引用、缺失输入处理和动态结果视图。Agent 路径不包含业务写入。

退出证据：代表性评估证明工具选择可靠、回答有事实依据、数据访问受控、失败可以恢复，并且用户查询或计算时间有可衡量的下降。

### 阶段 2：BOM 与报价决策支持

增加可审核的 BOM 提取或草稿、版本化成本计算、历史对比和报价方案。所有推断字段都必须提供来源并经过人工确认。

退出证据：报价周期和人工操作时间得到改善，同时没有产生不可接受的成本偏差或审核负担。

### 阶段 3：APS 模拟与跨领域协调

增加产能与约束模型、排程模拟、不可行原因解释和方案对比。通过 Core Agent 协调排程风险、物料齐套状态和报价假设。

退出证据：在受控试点中，排程速度、计划达成率和交付风险识别能力得到改善。

### 阶段 4：受治理的业务写入

通过明确的审批工作流、幂等 Service API、职责分离和回滚或补偿机制，引入经过筛选的 L3 操作。应从低风险、可逆操作开始，并在运行审查通过后再扩大范围。

退出证据：审批和执行可以完整追溯；未授权和重复写入被阻止；异常处理和回滚流程经过演练。

### 阶段 5：选择性演进为多智能体

只有当评估和责任归属数据表明单个 Core Agent 已成为限制因素时，才拆分专业 Agent。所有 Agent 继续使用统一的用户任务模型和共同治理机制。

退出证据：多智能体设计改善了明确的质量、延迟或可维护性指标，同时没有削弱安全性、可预测性或用户理解程度。

## 业务价值与系统健康指标

每次发布都应明确基线、目标、观察周期和责任人。指标应按照工作流和用户群体分别统计，不能简化为单一的“AI 准确率”。

| 维度 | 候选指标 |
|---|---|
| 速度与人效 | 周期时间、人工操作时间、交接次数、积压时长、每位计划员完成的任务数 |
| 质量 | 首次接受率、修改率、成本偏差、排程可行率、缺料判断的精确率与召回率 |
| 经营结果 | 准时交付率、计划达成率、物料齐套率、紧急采购、库存周转率、过量库存 |
| 采用与信任 | 活跃使用率、建议接受率、人工覆盖原因、任务放弃率、用户报告的信任度 |
| 安全与控制 | 被阻止的未授权尝试、审批绕过、过期数据拒绝、重复写入防护、审计完整率 |
| 可靠性与成本 | 工具成功率、任务完成率、P95 延迟、恢复率、每个完成任务的计算成本 |

指标必须区分未经修改直接接受的草稿和经过重大修改后批准的草稿。人工覆盖和拒绝是有价值的学习信号，但未经审核不得自动用于训练或改变生产行为。

## 跨领域要求与待决事项

在实现范围扩展到 V0.1 之外前，项目应明确：

- 租户、角色和数据访问模型；
- 订单、产品、BOM、库存快照、资源和策略的规范标识与版本管理；
- 任务、事件、审批和审计 Schema；
- 仅使用授权数据或明确合成数据构建的评估数据集；
- 模型和提示词的变更控制、回归评估及回滚；
- 优化目标，以及谁有权修改目标权重；
- 数据过期阈值和并发处理方式；
- 人工升级和运行支持路径；
- 适用司法辖区的隐私、保留和自动化决策要求。

这些都是必须主动做出的设计决策，不能隐藏在提示词中，也不能推迟到系统开始自主执行时再处理。
