# FlowOS AI 开发规划

## 目的

本规划将当前代码仓库基础和 AI 制造操作系统的长期方向转化为可执行的交付顺序。在增加 Core Agent 或扩展到 BOM 报价和 APS 之前，优先完成一条可信的端到端业务流程。

本规划使用相对 Sprint，而不是承诺具体日历日期。一个 Sprint 表示一个短周期、可演示的交付阶段；可以根据团队产能调整范围，但不能降低验收门槛。

## 当前基线

截至初始基础里程碑，仓库已包含：

- 使用版本化 `/api/v1` 前缀和健康检查端点的 FastAPI 应用；
- SQLAlchemy、PostgreSQL 连接池、Alembic 和首个数据库迁移；
- 最小化的 `customer` 与 `sales_order` 持久化模型；
- 有结果上限的销售订单查询 Schema、Repository 和 Service；
- 3 个通过的后端测试和通过的 Ruff 检查；
- 用于 PostgreSQL 和 API 的本地 Docker Compose；
- 产品、架构、业务规则、合规和 AI 方向文档；
- 规划中的 React、TypeScript 和 Vite 目录结构，但尚无前端应用。

当前基线仍存在以下重要缺口：

- 销售订单查询已存在于 HTTP 层以下，但尚未通过路由暴露；
- 订单尚无计算物料需求所需的明细、产品、数量或单位；
- 尚无 BOM 版本、物料主数据、库存、预留、在途供应和单位换算；
- 尚未实现库存缺口和采购建议的领域计算；
- 尚无持久化任务、快照、规则版本、审计或审批模型；
- 尚无身份认证、权限控制、租户隔离和生产数据控制；
- 尚无 PostgreSQL 集成测试和持续集成；
- 前端尚未初始化；
- 按照当前设计，尚未集成 LLM 或 Agent。

仓库当前没有提交历史。建立可审核的版本控制基线，是规范化交付的前提。

## 交付策略

第一个产品切片保持为：

```text
查找订单
    -> 根据版本化 BOM 计算物料需求
    -> 读取明确的库存与供应快照
    -> 计算并解释缺口
    -> 创建无约束力的采购建议草稿
    -> 审核或丢弃草稿
```

该流程应首先能够脱离 Agent，通过普通 API 和结构化 UI 完整运行。只有当 API、计算、任务状态和审计证据足够可靠后，才增加 Core Agent。这样可确保 Agent 协调的是已经验证的能力，而不会成为堆积未完成业务规则的地方。

## 工作流

以下 6 条工作流贯穿各里程碑：

1. **产品与领域：**术语、规则、异常行为、合成场景和验收标准。
2. **后端能力：**契约、确定性领域逻辑、Service、持久化、迁移和 API。
3. **前端工作流：**结构化查询、缺料解释、草稿审核、任务状态和错误处理。
4. **信任与治理：**身份、授权、租户、审批、审计证据、数据最小化和保留策略。
5. **质量与运维：**单元、契约、集成和端到端测试；CI；日志；指标；链路追踪；备份与恢复。
6. **AI 编排：**评估、工具契约、Core Agent、有依据的解释，以及受控的多 Agent 演进。

## 路线图概览

| 阶段 | 参考周期 | 结果 | 依赖 |
|---|---:|---|---|
| 0. 基线与决策 | 1 个 Sprint | 可审核的仓库和确认后的 V0.1 领域契约 | 当前基础 |
| 1. 订单与需求基础 | 1–2 个 Sprint | 可查询订单及基于版本化 BOM 的物料需求 | 阶段 0 |
| 2. 库存与缺口引擎 | 2 个 Sprint | 可复现、可解释的缺料分析 | 阶段 1 |
| 3. 采购建议草稿 | 1–2 个 Sprint | 具有生命周期和审计的可审核草稿 | 阶段 2 |
| 4. 结构化 Web 工作流 | 2 个 Sprint | 可用的端到端浏览器体验 | 阶段 1–3 的 API |
| 5. 生产就绪门槛 | 2–3 个 Sprint | 具备运行控制的授权试点基础 | 阶段 0–4 |
| 6. 面向 L1/L2 的 Core Agent | 2–3 个 Sprint | 使用自然语言协调经过验证的工具 | 阶段 5 与 Agent 评估门槛 |
| 7. BOM 报价扩展 | 3 个以上 Sprint | 可审核的 BOM 与报价决策支持 | 阶段 6 的共享平台 |
| 8. APS 模拟 | 3 个以上 Sprint | 基于约束的排程方案与风险分析 | 可靠的产品、BOM、产能和物料数据 |

以上周期是针对小型专注产品团队的规划区间，不是发布日期承诺。只有当共享身份、任务、版本和审计基础稳定后，阶段 7 和阶段 8 才可以并行。

## 阶段 0：基线与领域决策

### 目标

- 创建首次 Git 提交，并定义轻量的评审流程。
- 为后端测试、代码检查、迁移验证和密钥扫描增加 CI。
- 与获得授权的领域相关方确认 V0.1 术语和范围边界。
- 使用合成示例将占位规则转化为明确、可测试的决策。

### 必须确定的事项

- 哪些订单状态可以进入计算，以及何时固定订单需求快照。
- 订单行数量、单位、颜色、尺码和产品或款式的表达方式。
- BOM 版本选择和生效日期规则。
- 物料计量单位、换算、精度、舍入和损耗规则。
- 合格现存量、保护库存、预留、分配和在途供应规则。
- 快照新鲜度，以及分析期间数据发生变化时的处理方式。
- 采购舍入、最小订购量和仅生成草稿的范围边界。
- 覆盖正常路径和重要异常的合成场景集。

### 交付物

- 版本化领域术语表和 V0.1 决策记录；
- API 错误信封和资源命名约定；
- 测试数据工厂和确定性的合成测试数据；
- CI 流程和已记录的本地验证命令；
- 审核所有未跟踪文件后的首次仓库提交。

### 退出门槛

团队能够从输入到输出完整解释 V0.1 计算，不依赖任何未声明规则；每项已接受规则至少有一个合成示例或计划中的测试。

## 阶段 1：订单与物料需求基础

### 后端范围

- 通过 HTTP 路由暴露现有的受限销售订单查询。
- 增加分页或有文档的有限列表契约，避免没有边界的扫描。
- 引入最小化的产品或款式、销售订单行、物料、BOM 头或版本及 BOM 明细模型。
- 有意保持商业数据范围狭窄，不复制外部 ERP 数据结构。
- 增加纯领域函数，通过明确选定的 BOM 版本展开订单数量。
- 返回带有来源订单行、BOM 明细、数量、单位、损耗、舍入和规则版本的需求明细。

### 质量范围

- 为数量、小数精度、单位不匹配、缺少 BOM、BOM 未生效，以及零值和负值输入增加单元测试。
- 使用一次性数据库运行 PostgreSQL 迁移和 Repository 集成测试。
- 检查路由状态码和响应 Schema 的 OpenAPI 契约。

### 退出门槛

给定一张符合条件的合成订单，API 能根据指定 BOM 版本生成预期的物料需求明细；无效或不完整输入会返回结构化、可操作的错误。

## 阶段 2：库存模型与确定性缺口引擎

### 后端范围

- 仅根据 V0.1 需要增加库存位置、库存批次或余额、预留或分配、保护库存和在途供应模型。
- 定义不可变或可重建的库存与供应快照，并由每次分析引用。
- 将单位换算与缺口算术分开实现。
- 实现版本化的纯领域计算：

```text
总需求量 = 订单需求量 + 明确的附加用量
可用供应量 = 合格现存量 - 保护库存 - 已有占用 + 合格在途量
缺口 = max(0, 总需求量 - 可用供应量)
```

- 返回计算明细、排除项、警告、数据新鲜度和来源引用。
- 增加分析 API；相同订单、规则版本和输入快照的请求必须具备幂等性。

### 质量范围

- 使用表格驱动测试覆盖边界、小数行为、单位换算、批次与颜色、不合格在途量、保护库存和已有占用。
- 可增加基于属性的测试，验证缺口非负、兼容单位转换前后数量守恒等不变量。
- 集成测试验证事务边界和并发快照行为。

### 退出门槛

每个合成缺口结果都能根据已存储的输入和规则版本复现。审核人员无需阅读日志或源代码，就能将每个输出数字追溯到纳入和排除的供应。

## 阶段 3：采购建议草稿与任务生命周期

### 后端范围

- 为分析和草稿生成增加持久化任务记录及状态流转事件。
- 首先实现 V0.1 所需状态：`draft`、`ready`、`running`、`needs_input`、`completed`、`discarded` 和 `failed`。
- 增加采购建议草稿及明细模型，并引用准确的缺口结果。
- 应用明确的包装、舍入和最小数量规则；显示尚未确定的供应商、价格、税费、提前期和商务条款。
- 支持创建、读取、修改和丢弃；不得提交采购订单或联系供应商。
- 草稿创建使用幂等键；修改使用乐观并发控制或版本检查。
- 为状态流转和重要字段变更生成只追加的审计事件。

### 退出门槛

用户能够根据缺口分析创建草稿、理解每个建议数量、修改允许编辑的字段并丢弃草稿。重复请求不会创建重复草稿，完整生命周期可以在审计历史中查看。

## 阶段 4：结构化 Web 工作流

### 基础建设

- 在现有前端目录中初始化 React、TypeScript 和 Vite。
- 增加路由、类型明确的 API 客户端、生成或验证后的 API 类型、错误处理和轻量设计变量层。
- 基于可访问性和可维护性选择组件方案，而不是追求视觉新奇。

### 用户流程

1. 查询并选择一张合成销售订单。
2. 检查订单明细和选定的 BOM 版本。
3. 运行物料缺口分析，通过持久化任务状态查看进度。
4. 查看包含需求、合格供应、排除项、缺口、新鲜度和警告的缺料表。
5. 创建并编辑明确标记的采购建议草稿。
6. 查看任务时间线，并丢弃或导出草稿。

### 体验要求

- 采用桌面端优先的响应式布局，适合业务操作表格。
- 支持键盘操作、易读的状态和错误提示，以及无障碍标签。
- 浏览器端不重复实现业务计算。
- 明确设计空数据、加载中、数据过期、数据不完整、冲突和失败状态。
- 只能使用合成测试数据和截图。

### 退出门槛

代表性用户无需数据库控制台或 API 工具即可完成端到端流程，能够识别缺料原因，并且不会将草稿误认为已经下达的订单。

## 阶段 5：生产就绪门槛

在使用任何经过授权的真实业务数据或开展用户试点前，必须完成本阶段。

### 安全与治理

- 身份认证及 Session 或 Token 生命周期。
- 在数据访问中强制执行租户隔离，并测试跨租户拒绝行为。
- 覆盖 L1 查询和 L2 草稿的角色权限模型；L3 保持禁用。
- 审计保留、敏感值最小化、加密、密钥管理，以及依赖和许可证审查。
- 针对 API、文件、未来提示词和工具调用的威胁模型。

### 运维

- 结构化日志包含关联、任务、操作者和租户标识，但不包含敏感载荷。
- 记录 API 和任务延迟、失败、计算结果及草稿生命周期指标。
- 建立健康检查、就绪检查、迁移、备份、恢复和事件处理流程。
- 为持久化长任务建立支持重试和死信处理的后台任务机制。
- 使用代表性的合成数据量测试数据库索引和查询计划。

### 产品验证

- 为 V0.1 周期时间、人工操作时间、缺料审核质量、草稿修改率和任务完成率建立基线与目标。
- 在任何授权数据试点前，使用合成数据开展受控可用性测试。
- 记录支持责任、升级路径和回滚标准。

### 退出门槛

安全和运维审查批准系统用于预定试点范围。跨租户测试、恢复演练、审计完整性、失败恢复和用户验收全部通过。

## 阶段 6：用于查询与分析的 Core Agent

### 前置条件

只有当端到端确定性工作流、授权、任务状态和审计事件稳定后，才开始开发 Core Agent。工具契约应首先能够通过 UI 和 API 独立产生价值。

### 初始 Agent 范围

- 理解查找订单、解释缺料、比较输入假设或准备采购建议草稿等有明确边界的请求。
- 只规划和调用白名单中的 L1 和 L2 工具。
- 引用所使用的业务对象、快照和规则版本。
- 对缺失的必要输入进行询问，而不是猜测。
- 使用与普通工作流相同的结构化结果组件。
- 不得执行 L3 操作、任意 SQL、外部消息或供应商提交。

### Agent 平台工作

- 映射到普通 Service API 的类型化工具注册表。
- 与公共任务模型关联的持久化 Agent 运行和步骤记录。
- 上下文最小化与脱敏策略。
- 模型、提示词和工具 Schema 版本管理。
- 超时、重试、取消和恢复行为。
- 基于合成场景的离线评估套件，覆盖工具选择错误、数据过期、提示词注入、授权、缺少输入和任务不可行等情况。

### 退出门槛

Agent 在工具选择正确率、有依据的解释、任务完成、授权安全、延迟和成本方面达到约定阈值。失败仍能通过结构化 UI 恢复，普通 API 继续能够脱离 Agent 工作。

## 阶段 7：BOM 与报价能力

共享平台验证完成后，将其作为下一个专业工具领域进行开发：

- 具有来源记录和授权控制的产品资料及文档导入；
- 将提取结果作为可审核的候选字段，绝不静默接受；
- BOM 草稿和版本工作流；
- 物料价格来源及有效期跟踪；
- SMV、人工、制造费用、损耗、币种、毛利和数量阶梯策略；
- 确定性的报价方案和成本明细；
- 仅使用授权数据进行历史对比；
- 报价周期、人工操作时间、首次完整率、修改次数，以及报价与实际成本偏差指标。

应先实现人工结构化输入，再引入文档导入和模型辅助提取，从而能够依据稳定契约衡量提取质量。

## 阶段 8：APS 模拟能力

APS 依赖可靠的上游主数据，初期应以方案模拟为主：

- 资源、日历、班次、技能、产线、工序、产能和换线；
- 订单优先级、承诺日期、物料齐套、在制品和冻结区间；
- 明确的硬约束与软约束，以及版本化的目标权重；
- 生成可行计划，或返回结构化的不可行原因；
- 方案对比、甘特图或产能视图；
- 排程时间、准时交付率、计划达成率、利用率、换线损失和人工重排指标。

发布或修改生产计划仍属于 L3 操作，不在初始模拟里程碑范围内。

## 阶段 9：受治理写入与选择性多 Agent 演进

只有在获得持续的试点证据后，FlowOS 才应增加经过筛选的 L3 操作。每项操作都需要明确预览、基于策略的审批、必要时的职责分离、幂等执行、过期状态拒绝，以及补偿或回滚流程。

只有当测量结果明确表明不同上下文、评估、权限、延迟或责任归属确有必要时，才应将 Core Agent 拆分为专业 Agent。BOM、APS 和库存专业 Agent 必须复用现有业务工具和公共任务与审计模型。多 Agent 拓扑是一种实现选择，不是成功指标。

## 共享技术架构决策

以下事项应在出现首个实际使用方时，通过简短的架构决策记录确定：

- 租户和操作者信息如何在 API、Repository、任务和审计层传递；
- 同步执行与后台执行的阈值；
- 任务事件的存储和前端传递方式，包括轮询、服务器发送事件（SSE）或 WebSocket；
- 不可变快照与可重建版本引用的选择；
- API 分页、筛选、幂等、并发和错误标准；
- 前端 API 类型采用自动生成还是人工维护；
- 小数、币种、计量单位、时区和时间戳约定；
- APS 优化引擎边界和求解器选择；
- 未来报价输入所需的文档或对象存储及恶意文件扫描；
- Agent 发布所需的模型供应商抽象、评估晋级和回滚机制。

避免在工作流需要之前提前增加基础设施，但身份、租户、可审计性和版本管理不能推迟到接入真实数据之后。

## 每个产品增量的完成定义

只有满足以下条件，一个增量才算完成：

- 已记录用户结果和不在范围内的行为；
- API 和 UI 契约明确使用单位、币种、时间和生命周期状态；
- 确定性规则具有以边界为重点的单元测试；
- 涉及 SQL 语义的 Repository 行为具有 PostgreSQL 集成测试；
- 在 Service 和 API 边界测试授权及租户隔离；
- 数据库迁移具有升级路径，以及安全回滚或前向修复方案；
- 错误结构化、可观察，并且用户能够理解；
- 重要操作会产生审计记录和任务状态；
- 测试、示例、截图和演示全部使用合成数据；
- 文档和 OpenAPI 已更新；
- 已通过真实感较强的端到端场景完成演示。

## 建议的后续三个 Sprint

### Sprint 1：使基础可审核

- 审核当前所有未跟踪的仓库内容，并创建首次提交。
- 增加 CI 和统一的本地验证流程。
- 确定 V0.1 术语表、合成场景和领域决策。
- 暴露并测试现有销售订单查询 API。
- 定义 API 错误信封和分页约定。

演示：通过 API 查询 `SYN-SO-0001`，展示具有范围限制和明确类型的成功及错误响应。

### Sprint 2：计算物料需求

- 增加最小化的产品或款式、订单行、物料、BOM 版本和 BOM 明细模型及迁移。
- 实现包含单位、损耗、舍入和版本证据的确定性需求展开。
- 增加单元测试和 PostgreSQL 集成测试。
- 增加合成种子数据或测试工厂，但不提供可用于生产数据导入的路径。

演示：选择一张合成订单，将每条物料需求解释并追溯到订单和 BOM 输入。

### Sprint 3：计算并解释库存缺口

- 增加最小化的库存、占用、保护库存、在途和快照模型。
- 将单位换算和缺口引擎实现为相互独立的纯领域组件。
- 增加分析 API、可复现证据、警告和边界测试。
- 起草下一采购建议里程碑所需的任务和审计事件 Schema。

演示：运行多个合成场景，展示无缺口、部分缺口、供应被排除、单位换算、数据过期和缺少输入。

## 发布决策规则

- 在首批 API 契约足够稳定之前，不开始完整前端工作流，但应尽早使用简单 API 演示进行验证。
- 在确定性 V0.1 工作流和信任控制通过退出门槛前，不增加 Core Agent。
- 在阶段 5 就绪审查前，不接收真实生产数据。
- 不能仅因为 L2 草稿足够准确就增加 L3 执行；审批和运行恢复是独立能力。
- 没有证据证明专业化可以改善明确指标时，不拆分为多个 Agent。

该顺序既能保持近期工作范围聚焦，又能确保每个增量成为 AI 制造操作系统可复用的基础。
